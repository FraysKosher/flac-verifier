# Contributing to FLAC VERIFIER

Thanks for taking the time to look at this project. It is a personal tool that
became public for an international audiophile community, so contributions are
welcome as long as they keep the two things the project cares about: **honest
results** and **documented limits**.

This guide covers what you need to build, test and package the project, and what
is expected of a change before it becomes a pull request.

---

## Language of the project

- Everything the user can see is in **English**: the GUI, the CLI prompts, the
  PDF report, the engine messages and the values of the JSON protocol, plus all
  the documentation (`README.md`, this file, `CHANGELOG.md`).
- Comments and docstrings inside the code are still in **Spanish**. That is a
  known pending task, not a rule to be proud of: new comments may be written in
  either language, but please do not mix both inside the same function.
- `tests/test_idioma.py` enforces the boundary. It walks the text literals of the
  application and tool modules and fails if it finds Spanish characters or
  Spanish words in them. Comments and docstrings are ignored on purpose, and JSON
  protocol keys and reportlab style names are allow-listed because they are
  internal identifiers. If you add a user-visible string, it must be English or
  that test will fail.

---

## Requirements

- **Python 3.10** (developed and verified with 3.10.11 on Windows). The packaging
  script only enforces 3.8 or newer, but the test suite is validated on 3.10.
- Dependencies:

  ```
  pip install -r requirements.txt
  ```

  Four of them are optional and the program degrades gracefully without them:

  | Dependency | Needed for |
  |---|---|
  | `numpy`, `scipy`, `soundfile`, `mutagen` | The analysis itself (required) |
  | `matplotlib` | PNG spectrograms and the images embedded in the PDF |
  | `reportlab` | The per-album PDF report |
  | `customtkinter` | The graphical interface |
  | `tkinterdnd2` | Dragging folders onto the window |

- The test suite needs **no extra dependencies**: it uses `unittest` from the
  standard library.

## Running the tests

```
python -m unittest discover -s tests           # summary
python -m unittest discover -s tests -v        # verbose, one line per test
python -m unittest tests.test_md5              # a single module
```

- The suite is **229 tests** and takes about **60 s**.
- The FLAC fixtures are generated by the tests themselves in a temporary
  directory, so no audio files have to be downloaded or committed.
- Two tests are skipped depending on the environment, and both skips are the
  correct answer:
  - the one that checks that the parallel path really uses processes, when the
    system does not allow creating them (a sandbox or a container without the
    required permissions);
  - the one that covers running **without** `tkinterdnd2`, which is skipped when
    the library *is* installed, because then that scenario cannot be reproduced.
- The window tests need a display. On a CI machine with no desktop, skip them:

  ```
  FLAC_VERIFIER_SIN_GUI=1 python -m unittest discover -s tests
  ```

- `tests/test_veredictos.py` generates real MP3 transcodes with `ffmpeg` when it
  is on the `PATH`, and skips those cases otherwise. Installing `ffmpeg` gives you
  more coverage locally.

## Where the code goes

The architecture is deliberately flat, and one rule keeps it that way:

> **All the analysis logic lives in `motor_flac.py`.** The presentation layers
> must not reimplement it.

| Module | Responsibility |
|---|---|
| `motor_flac.py` | The engine: decoding, MD5 verification, clipping, dynamic range, low-bit usage, spectral analysis, scoring, cache, process pool and the CLI with the JSON protocol |
| `verificar_flac.py` | CLI presentation only: it formats what the engine returns |
| `gui.py` | The window only: it launches the engine as a subprocess and paints events |
| `informe_pdf.py` | The PDF only: it draws what the engine returned |
| `main.py` | A thin flag dispatcher towards the four modules above. Nothing else |
| `build.py` | Builds and verifies the packaged executable |
| `comprobar_ejecutable.py` | Full check of the executable once built |

If a change needs a new measurement or a new threshold, it belongs in
`motor_flac.py`, and the presentation layers only render it. There are tests
(`tests/test_estructura.py` among others) that fail if a layer starts duplicating
engine logic, so a "quick fix" in the CLI or the GUI will be caught.

Two more invariants worth knowing before you touch anything:

- `multiprocessing.freeze_support()` must stay as the **first statement** of the
  `__main__` block of `main.py`. `tests/test_empaquetado.py` checks it.
- `VERSION_MOTOR` in `motor_flac.py` must be raised whenever any analysis
  calculation changes: it is what invalidates the caches written by earlier
  versions. It currently reads `VERSION_MOTOR = "9.0"`.

## Building and checking the executable

Packaging is Windows-only (PyInstaller, `onedir`, two executables) and is fully
automated:

```powershell
python -m pip install pyinstaller      # once
python build.py                        # cleans, builds and verifies (~1 min)
python build.py --no-clean             # reuse build/ for an incremental build
```

`build.py` checks the interpreter and PyInstaller, removes `build/` and `dist/`
unless `--no-clean` is passed, builds `flac_verifier.spec` and verifies that both
`.exe` files exist and answer `--version`.

Once built, run the full check — this is the script worth running on a machine
**without Python**, which is where a missing module really shows up:

```powershell
python comprobar_ejecutable.py --album "D:\Music\Album"
python comprobar_ejecutable.py                       # uses the test album, if present
python comprobar_ejecutable.py --quick               # only steps 1-3, no PDF, no window
python comprobar_ejecutable.py --folder "dist\FLAC_Verifier"   # another build folder
```

It runs 11 checks grouped into 7 steps (both executables answer, serial analysis,
parallel analysis with 8 processes, PDF and spectrograms, the command the GUI
builds plus the `--motor-cli` fallback, the window opening and closing cleanly,
and the frozen executable producing the same records as the source code, field by
field). Each step has its own time limit.

Two environmental notes:

- If the machine cannot create processes (a sandbox, a security policy), the
  engine falls back to serial on purpose and step 3 fails. That is not a broken
  build: run it in a normal console to verify the parallel path.
- The output of the executables is always redirected to a file, never to a pipe.
  Child processes inherit pipes and the end of file never arrives, so a piped
  read would wait forever. Please do not "simplify" that.

Packaging must not change the analysis: the same album must give the same
verdicts in source mode and in the executable. That is exactly what step 7
compares.

## Style conventions

- Follow the style of the surrounding code; there is no formatter configured.
  Four spaces, `snake_case` for functions and variables, `UPPER_CASE` for
  module-level constants, type hints where they help.
- **Comments and docstrings:** Spanish is accepted for now, English is fine too.
  The module header of every file explains *why* the code is the way it is, not
  *what* it does line by line; please keep that habit, because most of the
  non-obvious decisions in this project (the Nyquist-distance rule, the hi-res CD
  limit, the two executables) are documented there and in the README.
- **Anything the user can see must be in English**: window labels, CLI prompts,
  problem messages, PDF text, error strings and the values of the JSON protocol.
  `tests/test_idioma.py` enforces this; run it if you are unsure.
- Prefer clear, factual wording over marketing. The project is honest about its
  limitations (`README.md`, "Known limits") and that is a feature: if a change
  removes or hides a documented limit, it needs a measured justification.
- Do not introduce new runtime dependencies without discussing it first. numpy,
  scipy, soundfile and mutagen are the required set; matplotlib, reportlab,
  customtkinter and tkinterdnd2 are optional and must stay optional, with a clear
  message when they are missing.
- Keep performance in mind: the analysis runs as a single streaming pass with
  bounded memory, and the numbers in the README's performance section are part of
  the contract. A change that materialises the whole track in memory again will
  be visible.

## Adding a test

Tests live in `tests/`, one module per area, and use plain `unittest`. To add one:

1. Pick the right module, or create a new `tests/test_<area>.py` if the area is
   genuinely new. The existing modules are listed in the README's tests table.
2. Import the shared helpers from `tests/fixtures.py` (FLAC fixture generation,
   temporary directories, small signal builders) instead of writing your own
   audio files by hand. Fixtures are generated at run time, never committed.
3. Write a plain test method:

   ```python
   import os
   import sys
   import unittest

   RAIZ = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
   sys.path.insert(0, RAIZ)

   import motor_flac


   class MiTest(unittest.TestCase):
       def test_algo_concreto(self):
           resultado = motor_flac.analizar_archivo_datos(ruta, "center", None, False)
           self.assertEqual(resultado["veredicto"], "GENUINE LOSSLESS")
   ```

   Most tests need the project root on `sys.path`; the modules already at the top
   of the existing test files show the pattern.
4. Make it **deterministic and fast**. Synthesise the signal (sine sweeps, noise
   with a known ceiling, silence) instead of shipping audio, and keep every test
   under a second or two: the whole suite is around 60 s and is expected to stay
   there.
5. Use `self.skipTest("reason")` when the case genuinely cannot run in the
   current environment (no display, no `ffmpeg`, no permission to create
   processes), and say why in the message. Never silence a failure with a skip.
6. If the test pins an invariant rather than a behaviour (for example "the CLI
   does not duplicate the engine" or "`freeze_support()` is the first line"),
   say so in the module docstring: those tests are the reason the architecture
   has stayed put.

Then update the tests table in `README.md` if you added a module, and the count if
it changed.

## What to check before opening a PR

1. `python -m unittest discover -s tests` passes. The suite is 229 tests; if the
   count changed, say so in the PR description and update the README.
2. `python -m unittest tests.test_idioma` passes: no Spanish text has leaked into
   anything the user sees.
3. If you touched scoring, thresholds or spectral analysis: `VERSION_MOTOR` has
   been raised, the affected numbers in the README are updated, and the change is
   justified with a measurement (a fixture, a real file, a before/after table).
4. If you touched the presentation layers: no analysis logic was duplicated, and
   `tests/test_estructura.py` still passes.
5. If you touched packaging (`flac_verifier.spec`, `build.py`, `main.py`):
   `python build.py` succeeds and `python comprobar_ejecutable.py --album "<folder>"`
   passes all its checks, including step 3 (real processes) and step 7 (the
   executable gives the same records as the source code).
6. If you changed performance-relevant code, include the before/after figure for
   time and peak memory; the README's performance tables are expected to stay
   accurate.
7. Documentation is updated in the same PR: `README.md`, `CHANGELOG.md` (add your
   change under `Unreleased`) and this file when the workflow changes.
8. The diff is focused: one topic per pull request, no unrelated reformatting, and
   no `.py` file is rewritten wholesale.
9. Do not commit build output (`build/`, `dist/`, `__pycache__/`), generated media
   (`_spectrograms/`, PDF reports, PNG spectrograms) or private audio.
10. Describe what you changed and why, and — if the result is a limitation rather
    than a fix — say so plainly. An honest "still not detected in this case" is
    worth more here than an optimistic claim.
